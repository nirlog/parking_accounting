# parking_accounting

## 6.1 Формат хранения телефона

- Телефон хранится в едином нормализованном формате: только цифры.
- Допускается префикс `7` как часть канонического представления (без символа `+`).
- Любые разделители ввода (пробелы, дефисы, скобки и т.п.) удаляются на этапе нормализации перед сохранением.

## 6.2 Нормализация госномера

- Госномер должен сохраняться в нормализованном формате: `UPPERCASE`, без лишних пробелов (включая ведущие, хвостовые и повторяющиеся между символами).
- Для символов, визуально совпадающих в кириллице/латинице, применяется единое правило преобразования (выбранный алфавит фиксируется в реализации и используется консистентно).
- Нормализация выполняется до валидации, сохранения и сравнения значений.

## 10.2 Поиск по нормализованным данным

- Поиск должен выполняться по нормализованным полям (либо по вычисляемым нормализованным значениям), а не по «сырому» вводу.
- Запросы пользователя с пробелами, дефисами и иными разделителями должны находить те же записи, что и эквивалентный ввод без разделителей.
- Это правило обязательно для полей телефона и госномера.

## 6.4 Таблица `parking_cards`

### Политика `card_number`

Принято правило **вариант 3**: `card_number` **может повторяться после перевода предыдущей карты в архив**.

- Для неархивных карт `card_number` должен быть уникален.
- После архивации карты её `card_number` может быть использован повторно в новой активной карте.
- Рекомендуемая реализация в БД: частичный `UNIQUE`-индекс только для актуальных (неархивных) записей.

## 6.3 Отображаемый статус места

Единое правило отображения статуса:

1. Если у места есть **активная карточка**, отображаемый статус всегда `occupied`.
2. Ручной статус (`free` / `reserved` / `repair`) хранится как базовый и применяется только если **активной карточки нет**.


## 7.2 Дата и пересчёт статуса

1. Использовать локальную дату рабочего компьютера Windows без времени.
2. Часовой пояс — системный (`Europe/Moscow`).
3. Пересчёт статуса выполнять при открытии вкладки и после изменения оплат/карточек.

## 18. Защита от ошибок

### Контроль уникальности `card_number` среди неархивных карт

- Перед созданием карты система обязана проверять отсутствие **неархивной** записи с тем же `card_number`.
- При конкурентных операциях источником истины считается ограничение БД (частичный `UNIQUE` по неархивным записям).
- При конфликте с неархивной картой пользователь получает предсказуемую доменную ошибку (например, `CARD_NUMBER_ALREADY_EXISTS`).


### Правила закрытия карточки при активном оплачeнном периоде

1. При закрытии карточки, если `paid_until > closed_at`, система должна выполнить **возврат средств** за оставшийся оплаченный период.
2. Сумма возврата рассчитывается как стоимость **оставшихся дней минус текущий день** (день закрытия в возврат не включается).
3. В интерфейсе перед закрытием показывается предупреждение с расчётом возврата и подтверждение действия.
4. В отчётах такие карточки помечаются отдельным признаком `closed_with_active_paid_period = true`, чтобы их можно было фильтровать и отдельно анализировать.

## 14.2 Приоритет статусов

Зафиксирован единый приоритет:

1. Наличие активной карточки на место имеет безусловный приоритет — отображаемый статус `occupied`.
2. Ручной статус (`free` / `reserved` / `repair`) не теряется и хранится как базовый.
3. Базовый ручной статус используется для отображения только при отсутствии активной карточки.

## 14.4 Фильтры раздела «Места»

Правила попадания в группы фильтров:

- При **активной карточке** место всегда попадает в группу `occupied` (в группы `reserved` и `repair` в этот момент не попадает).
- При **отсутствии активной карточки**:
  - если ручной статус `reserved` — место попадает в группу `reserved`;
  - если ручной статус `repair` — место попадает в группу `repair`;
  - если ручной статус `free` — место попадает в группу `free`.

## 24. Критерии приёмки MVP

### Проверка поведения `card_number` при архивации

1. При создании карты с новым `card_number` запись создаётся успешно.
2. При повторной попытке создать карту с тем же `card_number`, пока предыдущая карта не архивирована, операция отклоняется с понятной ошибкой.
3. После перевода предыдущей карты в архив создание новой карты с тем же `card_number` выполняется успешно.

## 12.5 Правила проверки периодов оплат

Явно зафиксирована логика добавления нового оплаченного периода (`new`) относительно последнего существующего периода (`last`) для одной карточки:

1. **Допустимый последовательный сценарий**: `new.period_from = last.period_to + 1 day`.
2. **Пересечение периодов (блокирующий сценарий)**: если `new.period_from <= last.period_to`, операция отклоняется как пересечение.

### Примеры для однозначной реализации и тестов

#### Валидные примеры

- `last: 2026-01-01..2026-01-31`, `new: 2026-02-01..2026-02-28` → **валидно** (строго следующий день).
- `last: 2026-03-10..2026-03-10`, `new: 2026-03-11..2026-03-20` → **валидно** (последовательное продление).

#### Невалидные примеры

- `last: 2026-01-01..2026-01-31`, `new: 2026-01-31..2026-02-15` → **невалидно** (`new.period_from` совпадает с `last.period_to`, есть пересечение).
- `last: 2026-01-01..2026-01-31`, `new: 2026-01-15..2026-02-15` → **невалидно** (`new.period_from < last.period_to`, есть пересечение).
- `last: 2026-04-01..2026-04-30`, `new: 2026-04-20..2026-04-25` → **невалидно** (полностью внутри существующего периода).
