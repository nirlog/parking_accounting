# Техническое задание на разработку программы учёта автостоянки

**Версия:** 1.1, доработанная  
**Проект:** Автостоянка — учёт клиентов, автомобилей, мест и оплат  
**Целевая платформа:** Windows 10 / Windows 11

---

## 1. Назначение программы

Программа предназначена для локального учёта работы автостоянки на компьютере с Windows.

Основные задачи программы:

- ведение базы клиентов;
- ведение базы автомобилей;
- учёт парковочных мест;
- создание и хранение учётных карточек автостоянки;
- учёт оплат по каждой карточке;
- контроль срока оплаты;
- поиск клиентов, автомобилей и мест;
- просмотр свободных, занятых и проблемных мест;
- формирование простых отчётов;
- экспорт данных в Excel;
- резервное копирование базы данных.

Программа должна быть простой, понятной и удобной для пользователей пожилого возраста, в том числе для людей с плохим зрением.

---

## 2. Целевая платформа

Программа разрабатывается для операционных систем Windows 10 и Windows 11.

Программа должна работать как обычное настольное приложение с графическим интерфейсом.

Желательно, чтобы итоговая версия распространялась как `.exe`-файл или как папка с программой, которую можно запустить без установки Python на рабочем компьютере.

## 4. Общая логика работы

В программе существуют основные сущности:

1. Клиент.
2. Автомобиль.
3. Парковочное место.
4. Учётная карточка.
5. Оплата.
6. Настройки программы.

Один клиент может иметь один или несколько автомобилей.

Один автомобиль может быть связан только с одной активной карточкой автостоянки.

Одна учётная карточка связывает:

- клиента;
- автомобиль;
- парковочное место;
- дату постановки автомобиля;
- статус карточки;
- историю оплат.

Оплаты хранятся отдельно от карточек. Дата «оплачено по» не хранится вручную в карточке, а вычисляется по последней активной оплате.

## 5. Структура базы данных

### 5.1. Таблица `clients`

Назначение: хранение информации о клиентах.

| Поле | Тип | Обязательное | Описание |
|---|---:|---:|---|
| id | integer | да | Уникальный идентификатор клиента |
| surname | string | да | Фамилия |
| name | string | да | Имя |
| patronymic | string | нет | Отчество |
| phone | string | нет | Телефон в нормализованном виде, только цифры |
| document_type | string | нет | Тип документа |
| document_number | string | нет | Номер документа |
| address | string | нет | Адрес клиента |
| photo_path | string | нет | Относительный путь к фотографии клиента |
| created_at | datetime | да | Дата создания записи |
| updated_at | datetime | да | Дата последнего изменения записи |

Правила:

- ФИО в интерфейсе отображается в формате `Фамилия Имя Отчество`.
- Фото не хранить в SQLite как BLOB. В базе хранить только путь к файлу.
- Телефон хранится только цифрами, без пробелов, скобок, дефисов и знака `+`.
- Если пользователь ввёл телефон в формате `+7 921 443-15-83`, в базе сохраняется `79214431583`.
- Если пользователь ввёл 11 цифр, начинающихся с `8`, первая цифра заменяется на `7`.
- Если пользователь ввёл 10 цифр, в начало добавляется `7`.
- В интерфейсе телефон отображается в удобном виде, например `+7 921 443-15-83`.
- Поиск по телефону должен работать одинаково для ввода с разделителями и без разделителей.

Назначение: хранение информации об автомобилях.

| Поле | Тип | Обязательное | Описание |
|---|---:|---:|---|

- Госномер хранится в каноническом виде: верхний регистр, без лишних пробелов и дефисов.
- Канонический вид использует кириллические буквы.
- Латинские символы, визуально совпадающие с русскими буквами госномеров, преобразуются в кириллицу.

Таблица преобразования:

| Латиница | Кириллица |
|---|---|
| A | А |
| B | В |
| E | Е |
| K | К |
| M | М |
| H | Н |
| O | О |
| P | Р |
| C | С |
| T | Т |
| Y | У |
| X | Х |

Примеры нормализации:

| Ввод пользователя | Значение в БД |
|---|---|
| а 767 аб 178 | А767АВ178 |
| A767AB178 | А767АВ178 |
| А-767-АВ-178 | А767АВ178 |

Нормализация выполняется до валидации, сохранения и сравнения.

| Поле | Тип | Обязательное | Описание |
|---|---:|---:|---|
| id | integer | да | Уникальный идентификатор места |
| place_number | string | да | Номер места |

| Статус | Описание |
|---|---|

3. Базовый статус применяется только если активной карточки на место нет.

### 5.4. Таблица `parking_cards`

Назначение: хранение учётных карточек стоянки.

| Поле | Тип | Обязательное | Описание |
|---|---:|---:|---|
| id | integer | да | Уникальный идентификатор карточки |
| card_number | string | да | Уникальный номер карточки в программе |
| paper_card_number | string | нет | Номер бумажной карточки или бланка, если отличается от `card_number` |
| client_id | integer | да | Ссылка на клиента |
| vehicle_id | integer | да | Ссылка на автомобиль |
| place_id | integer | да | Ссылка на парковочное место |
| start_date | date | да | Дата постановки автомобиля на стоянку |
| closed_at | date | нет | Дата закрытия карточки / выезда |
| status | string | да | Статус карточки |
| attendant_name | string | нет | Дежурный, оформивший карточку |
| note | text | нет | Комментарий |
| closed_with_active_paid_period | boolean | да | Признак закрытия при действующем оплаченном периоде, по умолчанию `false` |
| refund_amount_kopecks | integer | нет | Расчётная сумма возврата в копейках |
| refund_days | integer | нет | Количество дней, за которые рассчитан возврат |
| refund_note | text | нет | Примечание по возврату |
| created_at | datetime | да | Дата создания записи |
| updated_at | datetime | да | Дата последнего изменения записи |

Статусы карточки:

| Статус | Описание |
|---|---|
| active | Машина стоит на стоянке |
| closed | Машина выехала, карточка закрыта, но доступна в обычном поиске |
| archived | Старая закрытая карточка, скрыта из основных списков и видна через фильтр «Архив» |

Правила переходов статусов:

| Переход | Разрешённость |
|---|---|
| active → closed | Разрешено |
| closed → archived | Разрешено |
| archived → closed | Разрешено только вручную при восстановлении из архива |
| closed → active | Запрещено, нужно создавать новую карточку |
| archived → active | Запрещено, нужно создавать новую карточку |

Правила уникальности:

- Одно место не может иметь две активные карточки одновременно.
- Один автомобиль не может иметь две активные карточки одновременно.
- `card_number` является внутренним уникальным номером карточки и не должен повторяться никогда.
- Если требуется указать номер бумажного бланка, используется поле `paper_card_number`; оно может повторяться.
- Источник истины для проверки уникальности — ограничение базы данных.

| status | string | да | Статус оплаты |

| Статус | Описание |
|---|---|
| active | Активная оплата |

Правила:

- В БД сумма хранится в копейках.

- Физическое удаление оплат в MVP не реализуется.
- Ошибочная оплата отменяется через статус `cancelled` с обязательным указанием причины.
- Редактирование активной оплаты требует подтверждения пользователя.

## 6. Вычисляемые значения

### 6.1. Оплачено по

Для карточки значение «оплачено по» вычисляется как:

```sql
MAX(payments.period_to)
```

Учитываются только оплаты, у которых:

```text
payments.status = active
```

Если активных оплат нет, отображать:

```text
Нет оплат
```

---

### 6.2. Статус оплаты

Для расчёта статуса оплаты используется локальная дата рабочего компьютера Windows. Время и часовой пояс не учитываются, используется только календарная дата.

| Условие | Статус |
|---|---|
| Активных оплат нет | Нет оплат |
| `paid_until < today` | Просрочено |
| `paid_until >= today` и `paid_until - today <= N дней` | Скоро закончится |
| `paid_until >= today` и `paid_until - today > N дней` | Оплачено |

Правила:

- Порог `N` по умолчанию равен 3 дням.
- Порог `N` хранится в настройке `payment_warning_days`.
- Пересчёт выполняется при открытии вкладки, после добавления оплаты, после отмены оплаты и после изменения карточки.
- Статусы в интерфейсе отображаются текстом, а не только цветом.

## 9. Раздел «Карточки»

### 9.1. Назначение

Раздел «Карточки» является основным рабочим экраном программы.

Раздел предназначен для:

- просмотра активных карточек;
- поиска клиента, автомобиля или места;
- добавления новой карточки;
- редактирования карточки;
- добавления оплаты;
- закрытия карточки;
- просмотра архивных карточек.

Кнопка печати карточки может присутствовать в интерфейсе MVP, но должна быть неактивной с сообщением «Печать будет добавлена в следующей версии».

### 9.2. Поиск

В верхней части экрана должно быть крупное поле поиска:

```text
Введите ФИО, номер машины, телефон или номер места
```

Рядом кнопка:

```text
[ Найти ]
```

Поиск должен работать по:

- фамилии;
- имени;
- отчеству;
- телефону;
- госномеру;
- номеру места;
- номеру карточки;
- номеру бумажной карточки, если он заполнен.

Правило поиска:

- поиск выполняется по нормализованным значениям;
- для телефона ввод с разделителями и без разделителей должен давать одинаковый результат;
- для госномера латинские и кириллические визуально похожие символы должны находиться одинаково.

### 9.3. Быстрые фильтры

Под поиском расположить крупные кнопки-фильтры:

```text
[ Все активные ] [ Просроченные ] [ Оплата скоро закончится ] [ Нет оплат ] [ Закрытые ] [ Архив ]
```

### 9.4. Таблица карточек

Основные колонки:

| Колонка | Описание |
|---|---|
| Место | Номер парковочного места |
| ФИО | Фамилия, имя, отчество клиента |
| Госномер | Номер автомобиля |
| Автомобиль | Марка и модель |
| Телефон | Телефон клиента |
| Оплачено по | Дата окончания последней активной оплаты |
| Статус оплаты | Оплачено / скоро закончится / просрочено / нет оплат |
| Статус карточки | Активная / закрыта / архив |

Технические поля не должны перегружать таблицу. Детали показываются в форме карточки.

### 9.5. Кнопки действий

Кнопки должны быть крупными:

```text
[ Добавить карточку ]
[ Открыть карточку ]
[ Добавить оплату ]
[ Закрыть карточку ]
[ Архивировать ]
[ Печать карточки ]
```

Если карточка не выбрана, действия для выбранной карточки должны быть неактивными или выводить понятное сообщение.

## 10. Форма добавления / редактирования карточки

Форма должна быть разбита на логические блоки.

### 10.1. Блок «Клиент»

Поля:

- Фамилия;
- Имя;
- Отчество;
- Телефон;
- Тип документа;
- Номер документа;
- Адрес;
- Фото клиента.

### 10.2. Блок «Автомобиль»

Поля:

- Марка;
- Модель;
- Цвет;
- Госномер;
- Фото автомобиля;
- Комментарий.

### 10.3. Блок «Стоянка»

Поля:

- Номер карточки;
- Номер бумажной карточки;
- Номер места;
- Дата постановки;
- Дежурный;
- Статус карточки;
- Комментарий.

### 10.4. Кнопки формы

Внизу формы:

```text
[ Сохранить ] [ Отмена ]
```

Кнопка «Сохранить» должна быть визуально основной.

### 10.5. Проверки при сохранении

При сохранении карточки программа должна проверить:

- заполнена ли фамилия клиента;
- заполнено ли имя клиента;
- заполнен ли госномер автомобиля;
- выбран ли номер места;
- не занято ли выбранное место другой активной карточкой;
- нет ли у данного автомобиля другой активной карточки;
- не используется ли уже такой `card_number`.

Если есть ошибка, программа должна показать понятное сообщение крупным текстом.

## 11. Форма оплаты

Форма оплаты должна быть максимально простой, так как это одно из самых частых действий.

### 11.1. Информационный блок

В верхней части формы показывать данные карточки:

```text
Клиент: Барбоскин Андрей Юрьевич
Место: 147
Авто: Toyota Camry, А767АВ178
Оплачено по: 27.09.2026
```

### 11.2. Поля оплаты

Поля:

- дата оплаты;
- период с;
- период по;
- сумма;
- номер квитанции;
- фискальный номер;
- принял оплату;
- комментарий.

### 11.3. Автоматическое заполнение периода

При открытии формы оплаты программа должна автоматически предложить период:

1. Если активных оплат ещё нет:
   - `period_from = start_date` карточки;
   - `period_to = start_date + 1 месяц - 1 день`.

2. Если активные оплаты уже есть:
   - `period_from = максимальная дата period_to по активным оплатам + 1 день`;
   - `period_to = period_from + 1 месяц - 1 день`.

Пользователь может вручную изменить даты.

### 11.4. Кнопки формы оплаты

```text
[ Сохранить оплату ] [ Сохранить и распечатать ] [ Отмена ]
```

Для MVP кнопка «Сохранить и распечатать» может быть неактивной с сообщением «Печать будет добавлена в следующей версии».

### 11.5. Проверки при сохранении оплаты

Программа должна проверить:

- заполнена ли дата оплаты;
- заполнен ли период с;
- заполнен ли период по;
- `period_to >= period_from`;
- сумма больше нуля;
- период оплаты не пересекается ни с одной активной оплатой по этой карточке.

Универсальное правило непересечения:

```text
Пересечение есть, если:
new.period_from <= existing.period_to
AND
new.period_to >= existing.period_from
```

Примеры:

| Существующий период | Новый период | Результат |
|---|---|---|
| 01.01.2026–31.01.2026 | 01.02.2026–28.02.2026 | Валидно |
| 01.01.2026–31.01.2026 | 31.01.2026–15.02.2026 | Невалидно |
| 01.03.2026–31.03.2026 | 01.02.2026–28.02.2026 | Валидно |

## 12. Закрытие карточки и расчёт возврата

### 12.1. Обычное закрытие

При закрытии карточки пользователь указывает дату закрытия `closed_at`.

Если активной оплаты нет или `paid_until <= closed_at`, карточка закрывается без расчёта возврата.

### 12.2. Закрытие при действующем оплаченном периоде

Если `paid_until > closed_at`, программа должна показать предупреждение:

```text
Карточка закрывается до окончания оплаченного периода.
Оплачено по: 27.09.2026
Дата закрытия: 20.09.2026
Дней к возврату: 7
Расчётная сумма возврата: ... руб.
```

Пользователь должен подтвердить закрытие.

После подтверждения в карточке сохраняются:

- `closed_with_active_paid_period = true`;
- `refund_days`;
- `refund_amount_kopecks`;
- `refund_note`, если пользователь указал комментарий.

### 12.3. Формула возврата

Расчёт производится по последней активной оплате, которая покрывает дату закрытия.

```text
Количество дней оплаченного периода = period_to - period_from + 1
Стоимость одного дня = amount_kopecks / количество дней оплаченного периода
Дни возврата = количество дней от дня после closed_at до paid_until включительно
Возврат = стоимость одного дня × дни возврата
```

Округление суммы возврата выполняется до целых копеек по обычному математическому правилу.

День закрытия не включается в возврат.

Пример:

| Параметр | Значение |
|---|---|
| Оплаченный период | 01.09.2026–30.09.2026 |
| Сумма оплаты | 9000 руб. |
| Дата закрытия | 20.09.2026 |
| Дни возврата | 10 дней, с 21.09.2026 по 30.09.2026 |
| Стоимость дня | 300 руб. |
| Возврат | 3000 руб. |

## 19. Защита от ошибок

Программа должна предотвращать типовые ошибки:

1. Создание двух активных карточек на одно место.
2. Создание двух активных карточек на один автомобиль.
3. Создание карточки с повторяющимся `card_number`.
4. Ввод оплаты с отрицательной или нулевой суммой.
5. Ввод оплаты с датой окончания раньше даты начала.
6. Пересечение периодов активных оплат по одной карточке.
7. Закрытие карточки без подтверждения.
8. Архивация карточки без подтверждения.
9. Отмена оплаты без указания причины.
10. Физическое удаление оплат.

Примеры доменных ошибок:

| Код ошибки | Сообщение |
|---|---|
| PLACE_ALREADY_OCCUPIED | Это место уже занято другой активной карточкой. |
| VEHICLE_ALREADY_ACTIVE | У этого автомобиля уже есть активная карточка. |
| CARD_NUMBER_ALREADY_EXISTS | Карточка с таким номером уже существует. |
| PAYMENT_PERIOD_OVERLAP | Период оплаты пересекается с уже существующей оплатой. |
| PAYMENT_AMOUNT_INVALID | Сумма оплаты должна быть больше нуля. |

## 25. Критерии приёмки MVP

MVP считается готовым, если выполнены условия:

1. Программа запускается на Windows.
2. При первом запуске создаётся SQLite-база.
3. Можно добавить клиента, автомобиль и карточку.
4. Можно указать парковочное место.
5. Нельзя создать две активные карточки на одно место.
6. Нельзя создать две активные карточки на один автомобиль.
7. Нельзя создать две карточки с одинаковым `card_number`.
8. Работает нормализация телефона.
9. Работает нормализация госномера.
10. Можно добавить оплату к карточке.
11. Нельзя добавить оплату с пересекающимся периодом.
12. Нельзя добавить оплату с суммой меньше или равной нулю.
13. Оплату можно отменить без физического удаления.
14. Программа автоматически показывает дату «оплачено по».
15. Программа автоматически показывает статус оплаты.
16. Можно найти карточку по ФИО, телефону, госномеру или месту.
17. Можно посмотреть список всех оплат.
18. Можно экспортировать оплаты в Excel.
19. Можно закрыть карточку.
20. При закрытии карточки с действующей оплатой рассчитывается возврат.
21. Опасные действия требуют подтверждения.
22. Интерфейс крупный и читаемый.
23. Основные кнопки имеют текстовые подписи.
24. Статусы отображаются текстом, а не только цветом.
25. Резервное копирование выполняется безопасным способом.

Дополнительные проверки доступности:

1. Основной текст не меньше 16 px.
2. Высота основных кнопок не меньше 44 px.
3. Высота строк таблицы не меньше 36 px.
4. Статусы понятны без цвета.
5. Сообщения об ошибках написаны простым языком.

## 27. Особые замечания

1. Программа должна быть максимально простой для пользователя.
2. Первый экран не нужно перегружать техническими полями.
3. Основной сценарий работы должен выполняться за минимальное количество кликов.
4. Приоритет — надёжность, понятность и сохранность данных.
5. База должна быть простой для резервного копирования.
6. Все данные должны храниться локально на компьютере пользователя.
7. Архитектура должна позволять в будущем добавить печать, фото, импорт, роли пользователей и дополнительные отчёты.
8. Финансовые записи не должны удаляться физически.
9. Вся логика нормализации телефона и госномера должна быть вынесена в отдельный сервис, чтобы одинаково применяться при сохранении, поиске и проверках.
