# parking_accounting

## 6.4 Таблица `parking_cards`

### Политика `card_number`

Принято правило **вариант 3**: `card_number` **может повторяться после перевода предыдущей карты в архив**.

- Для неархивных карт `card_number` должен быть уникален.
- После архивации карты её `card_number` может быть использован повторно в новой активной карте.
- Рекомендуемая реализация в БД: частичный `UNIQUE`-индекс только для актуальных (неархивных) записей.

## 18. Защита от ошибок

### Контроль уникальности `card_number` среди неархивных карт

- Перед созданием карты система обязана проверять отсутствие **неархивной** записи с тем же `card_number`.
- При конкурентных операциях источником истины считается ограничение БД (частичный `UNIQUE` по неархивным записям).
- При конфликте с неархивной картой пользователь получает предсказуемую доменную ошибку (например, `CARD_NUMBER_ALREADY_EXISTS`).

## 24. Критерии приёмки MVP

### Проверка поведения `card_number` при архивации

1. При создании карты с новым `card_number` запись создаётся успешно.
2. При повторной попытке создать карту с тем же `card_number`, пока предыдущая карта не архивирована, операция отклоняется с понятной ошибкой.
3. После перевода предыдущей карты в архив создание новой карты с тем же `card_number` выполняется успешно.
