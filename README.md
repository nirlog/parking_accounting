# Техническое задание на разработку программы учёта автостоянки

## 1. Название проекта

**Автостоянка — учёт клиентов, автомобилей, мест и оплат**

## 2. Назначение программы

Программа предназначена для локального учёта работы автостоянки на компьютере с Windows.

Основные задачи программы:

- ведение базы клиентов;
- ведение базы автомобилей;
- учёт парковочных мест;
- создание и хранение учётных карточек автостоянки;
- учёт оплат по каждой карточке;
- контроль срока оплаты;
- поиск клиентов, автомобилей и мест;
- просмотр свободных, занятых и проблемных мест;
- формирование простых отчётов;
- экспорт данных в Excel;
- резервное копирование базы данных.

Программа должна быть простой, понятной и удобной для пользователей пожилого возраста, в том числе для людей с плохим зрением.

---

## 3. Целевая платформа

Программа разрабатывается для операционной системы **Windows 10 / Windows 11**.

Программа должна работать как обычное настольное приложение с графическим интерфейсом.

Желательно, чтобы итоговая версия распространялась как `.exe`-файл или как папка с программой, которую можно запустить без установки Python на рабочем компьютере.

---

## 4. Технологический стек

Рекомендуемый стек:

- язык программирования: **Python 3.12+**;

## 5. Общая логика работы

В программе существуют следующие основные сущности:

1. Клиент.
2. Автомобиль.
3. Парковочное место.
4. Учётная карточка.
5. Оплата.

Один клиент может иметь один или несколько автомобилей.

Один автомобиль может быть связан только с одной активной карточкой автостоянки.

Одна учётная карточка связывает:

- клиента;
- автомобиль;
- парковочное место;
- дату постановки автомобиля;
- статус карточки;
- историю оплат.

Оплаты хранятся отдельно от карточек. Дата «оплачено по» не хранится вручную в карточке, а вычисляется по последней оплате.

## 7. Вычисляемые значения

### 7.1 Оплачено по

Для карточки значение «оплачено по» вычисляется как:

```sql
MAX(payments.period_to)
```

Если оплат нет — отображать `Нет оплат`.

### 7.2 Статус оплаты

| Условие (взаимоисключающее) | Статус |
|---|---|
| Оплат нет | Нет оплат |
| `paid_until < today` | Просрочено |
| `today <= paid_until <= today + N дней` | Скоро закончится |
| `paid_until > today + N дней` | Оплачено |

Правила вычисления:

1. Условия в таблице выше являются взаимоисключающими и применяются без дополнительного приоритета.
2. Использовать локальную дату рабочего компьютера Windows без времени.
3. Часовой пояс — системный (`Europe/Moscow`).
4. Пересчёт выполнять при открытии вкладки и после изменений оплат/карточек.
5. Порог `N` по умолчанию 3 дня, настраиваемый.

## 12. Форма оплаты

### 12.1 Информационный блок

Показывать: клиент, место, авто, оплачено по.

### 12.2 Поля

- дата оплаты;
- период с;
- период по;
- сумма;
- номер квитанции;
- фискальный номер;
- принял оплату;
- комментарий.

### 12.3 Автозаполнение периода

1. Если оплат нет:
   - `period_from = start_date`;
   - `period_to = start_date + 1 месяц - 1 день`.
2. Если оплаты есть:
   - `period_from = last.period_to + 1 день`;
   - `period_to = period_from + 1 месяц - 1 день`.

### 12.4 Кнопки

`[ Сохранить оплату ] [ Сохранить и распечатать ] [ Отмена ]`

### 12.5 Проверки

- заполнены дата оплаты, период с, период по;
- `period_to >= period_from`;
- сумма > 0;
- нет пересечения периодов.

Правило непересечения:

1. Валидно: `new.period_from = last.period_to + 1 day`.
2. Невалидно (пересечение): `new.period_from <= last.period_to`.

Примеры:

- Валидно: `2026-01-01..2026-01-31` + `2026-02-01..2026-02-28`
- Невалидно: `2026-01-01..2026-01-31` + `2026-01-31..2026-02-15`

## 18. Защита от ошибок

Программа предотвращает:

1. Две активные карточки на одно место.
2. Две активные карточки на один автомобиль.
3. Оплату с суммой <= 0.
4. `period_to < period_from`.
5. Пересечение периодов оплат.
6. Закрытие карточки без подтверждения.
7. Архивацию карточки без подтверждения.

Контроль `card_number`:

- проверка уникальности среди неархивных;
- источник истины при гонках — ограничение БД;
- при конфликте доменная ошибка `CARD_NUMBER_ALREADY_EXISTS`.

Закрытие карточки при активном оплачeнном периоде:

1. Если `paid_until > closed_at`, выполняется возврат за оставшийся период.
2. Возврат = стоимость оставшихся дней, не включая день закрытия.
3. Перед закрытием показывается предупреждение с расчётом и подтверждение.
4. В отчётах признак: `closed_with_active_paid_period = true`.

## 23. Этапы разработки

### Этап 1. MVP

1. Создание SQLite-базы.
2. Модели SQLAlchemy.
3. Главное окно PySide6.
4. Раздел «Карточки».
5. Добавление/редактирование карточки.
6. Список активных карточек.
7. Поиск по ФИО/телефону/госномеру/месту.
8. Добавление оплаты.
9. Раздел «Оплаты».
10. Расчёт «оплачено по».
11. Автостатус оплаты.
12. Закрытие карточки.
13. Экспорт оплат в Excel.

### Этап 2

1. Раздел «Места».
2. Фильтры мест.
3. Отчёт по оплатам за период.
4. Отчёт по просроченным.
5. Настройки интерфейса.
6. Резервное копирование.

### Этап 3

1. Фото клиентов/авто.
2. Печать карточки и квитанции.
3. Импорт из Excel.
4. Роли пользователей (при необходимости).
5. Журнал действий.

## 24. Критерии приёмки MVP

MVP готов, если:

1. Программа запускается на Windows.
2. При первом запуске создаётся SQLite БД.
3. Можно добавить клиента, автомобиль, карточку.
4. Можно указать место.
5. Нельзя создать 2 активные карточки на одно место.
6. Нельзя создать 2 активные карточки на один автомобиль.
7. Можно добавить оплату.
8. Автоматически показывается «оплачено по».
9. Автоматически показывается статус оплаты.
10. Работает поиск по ФИО, телефону, госномеру, месту.
11. Виден список всех оплат.
12. Работает экспорт оплат в Excel.
13. Можно закрыть карточку.
14. Опасные действия требуют подтверждения.
15. Интерфейс крупный и читаемый.
16. Кнопки имеют текстовые подписи.
17. Статусы показываются текстом, а не только цветом.

Дополнительные проверки:

18. Проверка поведения `card_number`: повтор до архивации запрещён, после архивации разрешён.
19. Проверка UI-метрик из раздела 9.
20. Проверка текстовой доступности статусов.
21. Проверка подтверждений для закрытия/архивации по пользовательскому сценарию.

## 26. Особые замечания

1. Программа должна быть максимально простой для пользователя.
2. Первый экран не перегружать техническими полями.
3. Основной сценарий — минимум кликов.
4. Приоритет: надёжность и понятность.
5. База должна быть удобна для резервного копирования.
6. Данные хранятся локально на компьютере пользователя.
7. Архитектура должна позволять в будущем добавить печать, фото, импорт и доп. отчёты.
